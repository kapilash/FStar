# Writing documentation for ulib

This guide is for anyone adding documentation to the F* standard library
(`ulib`). The text is written once, in the F* source. It is exported by
`fstar.exe --export_docs` and read by both a reference website and an MCP
server that agents use to search the library by type and contract.

## Where documentation goes

Put the documentation in a doc comment `(*| ... *)` directly before the
declaration. The doc comment is sugar for the `[@@doc [...]]` attribute.
The compiler stores the text and does not interpret it.

```fstar
(*| Returns the first element of a nonempty list. *)
val hd: l:list 'a{Cons? l} -> Tot 'a
```

- **Interface first.** If a module has an `.fsti`, document the `.fsti`.
  The export reads the interface, so documentation on the implementation
  is never shown.
- **One block per declaration.** In a `.fst` without an interface,
  document the `val` if there is one, otherwise the `let`. Do not document
  both: the `val` wins and the `let` text is lost.
- **Keep qualifiers and attributes.** A doc comment can go before or after
  `[@@ ...]` attributes and qualifiers such as `inline_for_extraction`.
- **Types describe their constructors.** A constructor cannot have its own
  documentation in the export, so describe the constructors and fields in
  the type's documentation.
- **Module and section introductions stay ordinary comments.** There is no
  place in the export for module-level text. Do not attach a module
  overview to the first declaration to make it appear.
- **Private declarations are not exported.** Ordinary comments are fine
  there.

### Forms the export does not cover

Effect declarations, effect abbreviations, `sub_effect` lifts, mutually
recursive `let rec ... and ...` groups and spliced declarations are not
exported. Keep their explanation in ordinary comments. Modules that have
such forms are listed in `ulib-docs-status.json` under `unsupported`, so the
gap is visible. `ulib_docs.py audit` finds candidates.

### Generated integer modules

`FStar.Int{8,16,32,64,128}` and `FStar.UInt{8,16,32,64}` are generated by
`.scripts/mk_int.sh`. Never edit them directly. Write their documentation in
`.scripts/FStar.UIntN.fstip` and `.scripts/FStar.IntN.fstip`, and write the
documentation for `n`, `byte` and `mul_wide` in the script itself. Then run
`bash .scripts/mk_int.sh` from the repository root.

The template text is shared by every width, so refer to the width as `n`.
Never write `UInt32` in a template or in the script: the script runs
`sed 's/UInt32.//g'` on the generated `FStar.UInt32` files, and that would
corrupt the text.

## What to write

Start with one sentence that stands alone in a search result: what the
declaration is for, not how it is written. Then add only what helps
someone use it correctly.

- **Functions.** Behavior, the meaning of arguments that are not obvious,
  bounds, what happens at the edges, and effect differences between
  variants (`map` is `ML`, `mapTot` is `Tot`). Name related variants.
- **Lemmas.** The property in words and when to reach for it. Mention SMT
  patterns when they matter: a lemma with an `SMTPat` usually does not need
  to be called. Mention preconditions a caller must establish.
- **Types and predicates.** The concept, its invariants, constructors and
  fields, and whether equality is decidable.
- **Assumptions and primitives.** Say what is specified and that it is
  assumed, not proved. Do not promise runtime behavior or performance that
  the specification does not state.
- **Aliases and deprecated declarations.** Name the equivalent or the
  replacement, fully qualified.

Do not restate the signature in prose, write empty filler ("This function
is a function"), guess at complexity, or include examples that have not
been checked. Read the contract and the definition before adapting an old
comment: old comments are sometimes wrong.

## The Markdown profile

Documentation is written in a conservative profile of the minimal
Markdown grammar that the verified F* Markdown parser will accept. The
profile avoids the grammar's edge cases until the parser can settle them.

Use:

- Paragraphs, separated by a blank line.
- ATX headings (`#` to `######`), rarely; most entries need none.
- Flat lists whose items start with `- ` and fit on **one line**. A wrapped
  list item becomes a paragraph, so use prose for anything longer.
- Inline code with single backticks for every identifier, operator and
  formula: `` `length s` ``, `` `@|` ``, `` `i < length s` ``.
- Inline links, `[text](target)`, for external pages.
- Fenced code blocks with three backticks.

Avoid raw HTML, tables, ordered lists, nested or indented lists, block
quotes, setext headings and indented code blocks. Avoid the legacy
`[name]` references and `{[ ... ]}` code blocks of older comments; write
`` `name` `` and fenced blocks instead.

Emphasis is rarely needed. If you must, write `*strong*` and `_emphasis_`,
with a single delimiter on each side. Never write CommonMark `**strong**`:
in this grammar `*` is strong and `_` is emphasis. Because a bare `_` or
`*` can start emphasis, an identifier like `rev_acc` or an operator like
`op_Star` must be in a code span. Escape a literal delimiter as `\*`.

Inline constructs never cross a line break. Keep each code span and link
on one line.

For now, refer to other library declarations by fully qualified name in a
code span, such as `` `FStar.Seq.Base.slice` ``. A link syntax for library
names will come with the website. Do not hardcode website URLs or anchors.

### Code examples

A fence with the info string `fstar` is a **checked example**. It must
appear verbatim in a file under `tests/docs/ulib/`, which the test suite
verifies. `ulib_docs.py lint` checks that it does. Use complete,
self-contained snippets that exercise one idea. For a fragment that is not
meant to check, use the info string `text`.

Examples sit inside an F* comment, so comment delimiters in an example
must be balanced: a stray `*)` ends the doc comment early.

Not every lemma needs an example. Add them for representative operations
and for proof idioms that are hard to guess from the signature.

## Checking your work

Documentation changes the source digest, so the checked files must be
rebuilt before exporting; the export refuses stale checked files.

Before that slow step, `lint-source` applies the same lint to the
`(*| ... *)` blocks of the files you edited, reading them as the lexer does:

```text
python3 .scripts/fstardoc/ulib_docs.py lint-source ulib/FStar.Seq.Base.fsti
```

```text
# 1. Re-verify ulib into the stage 2 cache.
env SRC=ulib/ FSTAR_EXE=stage2/out/bin/fstar.exe \
    CACHE_DIR=stage2/ulib.checked/ OUTPUT_DIR=stage2/ulib.ml/ \
    CODEGEN=OCaml TAG=lib make -f mk/lib.mk verify

# 2. Export, then report and check.
S=.scripts/fstardoc/ulib_docs.py
python3 $S export --fstar stage2/out/bin/fstar.exe \
    --cache stage2/ulib.checked --out _docs
python3 $S coverage --exports _docs -v --module FStar.Seq.Base
python3 $S lint --exports _docs --module FStar.Seq.Base
python3 $S check --exports _docs
python3 $S check --exports _docs --complete
# 3. Verify the checked examples.
make -C tests/docs/ulib
```

When every eligible declaration in a module is documented, add the module
to `completed` in `ulib-docs-status.json`. From then on `check` fails if a
declaration in it loses its documentation, fails the lint, or has an
example that is not checked. A declaration that should stay undocumented
goes under `exclusions` with a reason.

A module that cannot carry documentation at all goes under `blocked` with
a reason. Currently these are `Prims`, `FStar.Pervasives.Native` and
`FStar.Attributes`: `(*| ... *)` expands to `FStar.Attributes.doc`, which
these modules cannot depend on. `coverage` marks blocked modules with `!`,
and `check` rejects a module that is both blocked and completed.

`check --complete` also fails when a top-level module is neither completed
nor blocked. Use it to catch a new module added without documentation.

### What coverage counts

`coverage` counts `val`, `let`, `type` and `assume` declarations in the
exported, public surface. Constructors are counted separately as covered by
their type. Forms the export omits are not counted at all, which is why
they are tracked under `unsupported`. Full coverage of eligible
declarations is therefore not full coverage of every public name.

The lint is a conservative check written without a Markdown parser. Passing
it does not prove that the text conforms to the grammar; that awaits the
verified parser, which will run the fixtures in `fixtures/`.

## Current status

All 221 top-level modules are completed or blocked. 5,158 of 5,305
eligible declarations are documented; the remaining 147 are in the three
blocked modules. 409 constructors are covered by their parent type.

Still open:

- The blocked modules `Prims`, `FStar.Pervasives.Native` and
  `FStar.Attributes`.
- The public forms the export omits, listed per module under `unsupported`
  in `ulib-docs-status.json`: effects in `Prims`, `FStar.Pervasives`,
  `FStar.All` and `FStar.Tactics.Effect`, and mutually recursive
  definitions in six reflection and tactic modules.
- Module and section introductions, which have no place in the export.
- Grammar conformance and renderer parity, which await the verified parser.
- Source bugs found while documenting, listed in `ULIB_SOURCE_ISSUES.md`.
